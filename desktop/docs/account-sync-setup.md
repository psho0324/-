# PC 계정 동기화 연결 준비

작성일: 2026-11-13 (한국 시간). 이 문서는 0.1.3 개발 후보의 설정 안내입니다. 운영 Supabase나 Google 설정은 이번 작업에서 변경하지 않았습니다. 모든 배포는 사용자가 확인하고 “배포해”라고 승인한 뒤에만 진행합니다.

## 현재 사용할 수 있는 범위

로그인 없는 일정·할 일·목표·통계·기기 저장·백업과 로컬 알림은 계정 서버 없이 사용합니다. 2026-11-16 사용자가 제공한 플래너 프로젝트의 URL과 publishable 키를 `desktop/account-config.json`에 반영하고 형식을 확인했습니다. 같은 날 사용자는 SQL 적용, Google 공급자와 리디렉션 설정을 완료했다고 알려 주었고, Google 테스트 사용자 1명이 등록된 화면도 확인했습니다. 이는 사용자 보고와 설정 화면 확인이며 실제 로그인·서버 권한·기기 간 동기화 성공을 뜻하지 않습니다. 기존 공개 설치 파일과 홈페이지는 변경하지 않았습니다.

새 서버의 공개 인증 설정을 조회하려 했으나 작업 환경의 네트워크 프록시가 접속을 거부하여 실제 서버 응답은 확인하지 못했습니다. 이 결과를 키 유효성 확인이나 로그인 완료로 해석하지 않습니다. 동기화 SQL은 격리된 로컬 PostgreSQL 검사 16개를 다시 통과했습니다.

구글·이메일 로그인, 암호화된 세션 보관, 자동 동기화, 권한 검증 코드는 구현하고 가짜 계정과 격리된 SQL로 검사했습니다. 이메일 인증번호 템플릿·발송 설정, 실제 계정 로그인과 두 Windows PC의 인터넷 동기화는 추가 검증해야 합니다.

## 별도 Windows 계정 테스트 앱

2026-11-16 공개 배포와 분리한 Windows x64 압축 실행본을 준비했습니다. 원본 버전은 0.1.2로 유지하고, 별도 패키지 표식으로 0.1.3 후보임을 표시합니다. 기본 자료는 `%APPDATA%\\my-planner-account-test`에 저장하며 기존 앱의 기본 폴더와 분리합니다. 자동 업데이트·자동 시작·저장 폴더 변경을 차단하고 정식 배포 검사에서도 이 빌드를 거부합니다. 처음 열 때 기존 일정이 안 보이는 것은 분리된 빈 프로필을 사용하기 때문입니다.

만들기는 `node tools/build-account-test.cjs --out <빈 출력 폴더>`로 수행합니다. 임시 복사본에서만 테스트 표식을 넣고, 소스 package와 lock의 버전·내용을 바꾸지 않습니다. Windows 실행 파일과 전체 실행 폴더를 압축해 사용자에게 전달하며 Releases나 홈페이지에는 올리지 않습니다.

Node 17개 테스트 파일, 화면 검사 54개 시나리오와 최종 ASAR의 실행 모듈·전체 production 의존성 포함 검사를 통과했습니다. 최종 ASAR에서 추출한 코드를 실제 Linux Electron으로 실행하여 프로필 분리·저장·재실행·단일 실행·백업을 확인했습니다. 실제 Windows 실행·Windows 암호화·Google 로그인은 이 결과와 별개이며 사용자의 테스트 PC에서 확인해야 합니다.

## 필요한 외부 설정

1. 플래너용 Supabase 프로젝트를 정합니다. 홈페이지 관리자 기능과 일정 자료를 분리하기 위해 별도 프로젝트를 권장합니다. 같은 프로젝트를 쓰는 경우에도 홈페이지 `site_admins` 권한을 플래너에 재사용하지 않습니다.
2. 검토와 승인 후 그 프로젝트의 SQL Editor에서 `supabase/migrations/004_planner_sync.sql` 전체를 실행합니다. 새 플래너 전용 프로젝트에는 홈페이지용 schema/002/003을 설치할 필요가 없습니다. 004는 Supabase 기본 인증 테이블·역할을 사용하며 홈페이지 자료를 수정하지 않습니다.
3. 프로젝트 기본 URL과 publishable 키를 개발용 `desktop/account-config.json`에 설정합니다. 예시는 아래와 같습니다. 이 설정은 개발·패키징 단계에서 준비하며 일반 앱 사용자가 직접 API 설정을 입력하는 흐름은 제공하지 않습니다.

```json
{
  "url": "https://PROJECT.supabase.co",
  "publishableKey": "sb_publishable_PUBLIC_KEY"
}
```

URL에는 `/rest/v1/`을 붙이지 않습니다. 키는 publishable 또는 기존 anon 키만 허용합니다. 데이터베이스 비밀번호·service_role·secret 키·Google client secret을 앱이나 저장소에 넣지 않습니다. Google client secret은 Supabase 대시보드의 공급자 설정에서만 사용합니다.

### Google 로그인

1. Google Auth Platform에서 앱 정보와 OAuth 웹 클라이언트를 준비합니다. 테스트 단계에서는 사용할 Google 계정을 테스트 사용자에 등록합니다.
2. Google의 승인된 리디렉션 URI에는 Supabase가 안내하는 콜백 주소를 등록합니다. 일반 형태는 `https://PROJECT.supabase.co/auth/v1/callback`입니다.
3. Supabase Authentication의 Google 공급자를 켜고 Google 웹 클라이언트 ID·secret을 그 대시보드에 설정합니다.
4. Supabase 인증 Redirect URLs에 `http://127.0.0.1:42883/auth/callback*`를 허용합니다. 끝의 와일드카드는 요청별 임의 state 쿼리를 허용하기 위한 것입니다. 앱의 수신기는 정확한 경로·포트·state를 추가 확인하며 PKCE로 코드를 교환합니다.
5. PC 앱에서 Google 로그인을 누르면 기본 브라우저가 열립니다. 앱이 먼저 연 로컬 수신기로만 결과를 받아 비밀 검증값과 교환합니다. 사용자가 취소하거나 5분이 지나면 수신기를 닫습니다.

로그인은 기본 브라우저에서 수행하며 Google 비밀번호를 앱에 입력하거나 저장하지 않습니다. 한 PC에서 이미 로그인 중인 계정과 다른 계정으로 바꾸려면 먼저 로그아웃해야 합니다.

#### 로그인 완료 후 앱으로 돌아가기 (미배포 보완안)

Windows 설치 파일은 `tteodori-planner://open` 앱 열기 링크를 등록합니다. 로그인 완료 페이지에서 자동 열기를 시도하고, 차단되면 ‘플래너로 돌아가기’를 누를 수 있습니다. 브라우저가 외부 앱 열기를 물으면 ‘열기’를 선택합니다. 링크에는 인증 코드·토큰·계정 정보가 없으며 기존 앱 창만 엽니다. Google/Supabase 리디렉션 설정은 기존 loopback 콜백을 그대로 사용합니다.

NSIS 설치 후크가 실행 파일 경로를 등록하고 Windows에 연결 변경을 알립니다. 삭제 후크는 현재 등록이 자신의 경로일 때만 제거합니다. 앱을 실행하면 등록을 재확인합니다. 개발 실행과 비공개 테스트 ZIP에는 설치 후크를 실행하지 않습니다.

Windows가 백그라운드 앱의 포커스를 거부하면 작업 표시줄에 알립니다. 링크 등록 또는 브라우저의 앱 열기가 거부돼도 로그인 상태와 로컬 자료는 유지되며 작업 표시줄에서 돌아갈 수 있습니다. 브라우저가 자동 탭 닫기를 허용하지 않으면 완료 탭을 직접 닫아야 합니다. 개발 실행과 별도 계정 테스트 빌드는 일반 설치 앱의 링크 등록을 바꾸거나 그 링크로 다른 앱 창을 열지 않습니다.

### 이메일 인증번호

1. Supabase 이메일 공급자와 신규 가입 허용 범위를 확인합니다.
2. 인증 메일의 Magic Link 및 신규 가입 확인 템플릿에 `{{ .Token }}`을 표시하여 앱에 넣을 인증번호를 받을 수 있게 합니다. 기본 템플릿이 링크만 보여 준다면 번호 방식으로 사용할 수 없습니다.
3. 기본 메일 발송의 수신자·발송 제한을 확인하고 실제 베타 사용자에게 필요한 경우 SMTP를 설정합니다. 이 설정도 대시보드에서 관리합니다.
4. 앱에서 이메일로 번호를 요청하고 받은 번호로 로그인합니다. 같은 메일에 대한 연속 요청은 앱에서 잠시 제한하고 서버 제한도 따릅니다. 이번 검사에서 실제 메일은 보내지 않았습니다.

참고: [Google 공급자](https://supabase.com/docs/guides/auth/social-login/auth-google), [인증 리디렉션](https://supabase.com/docs/guides/auth/redirect-urls), [이메일 인증](https://supabase.com/docs/guides/auth/auth-email-passwordless).

## 자료 연결과 오프라인 동작

- 로그인과 자료 연결은 분리합니다. 처음에는 기존 기기 자료를 계정에 저장하는 선택을 명시적으로 확인한 뒤 연결합니다. 로그인만으로 파일 전체를 업로드하지 않습니다.
- 같은 PC에서 이전에 연결한 계정으로 돌아가면 그 계정의 별도 로컬 사본을 복구합니다. 로그인 없이 새로 작성한 자료는 별도로 보관하며 재연결 때 무조건 합쳐 넣지 않습니다. 앱에서 이 차이를 안내합니다.
- 일정·할 일·목표·카테고리·실천·못함 기록을 항목별로 맞춥니다. 설정은 이 기기에 유지합니다. 자동 시작·트레이·알림 사용·저장 위치 등이 다른 PC의 값으로 바뀌지 않습니다.
- 변경은 먼저 현재 기기에 저장합니다. 서버 요청 전에 재시도 번호와 전송 대기 상태를 별도 파일에 확정합니다. 응답 유실 후 같은 요청을 다시 보내도 서버에서 중복 생성하지 않습니다.
- 온라인일 때 짧게 모아 올리고, 보통 60초 간격으로 다른 기기의 변경을 확인합니다. 실패하면 자동으로 간격을 늘려 재시도하고 절전 복귀 때도 다시 확인합니다. 상대 기기의 변경이 항상 즉시 표시된다고 보장하지 않습니다.
- 서버가 같은 항목의 겹친 수정을 발견하면 양쪽 사본을 비공개 충돌 기록으로 보존하고 나중에 서버가 접수한 값을 현재 값으로 반영합니다. 설정에서 최근 충돌 사본을 파일로 저장할 수 있습니다. 이 내보내기는 최대 100건이며 응답 크기 제한에 따라 더 적을 수 있습니다. 전체 이력은 서버의 본인 전용 테이블에 남습니다.
- 정상 동기화에 팝업은 없습니다. 재로그인·저장 장애·중단된 자료 전환 복구처럼 조치가 필요한 상태는 설정에서 확인할 수 있습니다.
- 열린 편집창의 항목이 다른 곳에서 바뀌면 입력을 보존하고 저장을 막아 최신 내용을 덮어쓰지 않게 합니다. 계정 자료 전환 중에는 입력을 잠시 잠그며, 이전 계정에서 열어 둔 새 초안도 전환 후 다른 계정에 저장하지 못하게 합니다.

## 기기 파일과 복구

Windows 로그인 정보는 Electron safeStorage/운영체제 암호화로 `planner-account-session.enc`에 보관합니다. 암호화를 사용할 수 없으면 평문으로 저장하는 대신 계정 연결을 중단하며 로컬 앱은 계속 사용합니다. renderer에는 토큰을 보내지 않습니다.

`planner-sync-state.json`에는 대기 변경과 계정별 로컬 사본이 포함됩니다. 이는 개인 일정이 들어 있는 파일이므로 소스·Releases·홈페이지에 포함하지 않습니다. 로그아웃하면 계정 연결 전의 기기 자료로 돌아가며 계정별 사본은 그 PC에 별도로 남습니다. 다른 기기의 로그인은 해제하지 않습니다.

자료 전환 중 강제 종료로 파일 소유 계정을 확정할 수 없으면 파일을 그대로 두고 자동 업로드를 멈춥니다. ‘복구 자료를 이 기기에 보관’을 사용자가 선택하면 전환 전·후·현재 사본을 별도 복구 파일에 보존하고 현재 자료로 로그인 없이 사용합니다. 기존 계정 캐시도 유지합니다.

기존 OneDrive 등 폴더 파일 동기화와 계정 동기화는 동시에 사용하지 않습니다. 계정 연결 전에 저장 위치를 기본 위치로 바꾸고, 연결된 동안에는 저장 위치 변경을 막습니다. 자료 복원·가져오기를 하면 계정에 연결된 다른 기기에도 반영될 수 있으므로 먼저 백업합니다.

## 실제 연결 후 추가 확인

두 Windows 테스트 PC 또는 격리된 두 Windows 사용자로 Google·이메일 로그인, 오프라인 변경 후 연결, 동시 수정·삭제, 재실행, 로그인 만료, 로그아웃·다른 계정, 알림 표시·클릭을 검사합니다. 운영체제 암호화와 실제 메일/Google 흐름은 모의 검사 통과와 별개입니다. 실패한 상태에서 배포하지 않습니다.
