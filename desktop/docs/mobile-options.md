# 모바일 버전 선택지와 남은 작업

작성일: 2026-11-10. 현재 Windows 앱을 기준으로 작성한 설계 비교입니다. 이 문서는 앱·설정·빌드 코드를 변경하지 않으며, 모바일 버전을 구현하거나 배포했다는 의미가 아닙니다. PC 설치 앱의 수동 확인 9개 항목은 [검증 기록](../VERIFICATION.md)을 기준으로 사용자가 진행합니다.

사용자가 원하는 방향은 Notion처럼 **PC에서는 설치 앱을 쓰고, 휴대폰에서는 App Store·Google Play에서 앱을 설치해 사용하는 것**입니다. 아래 PWA는 선택지를 비교하기 위해 다루며, 합의한 스토어 앱 목표를 대신하는 기본 경로로 삼지 않습니다.

## 현재 코드에서 가져갈 수 있는 것

- [화면 HTML](../renderer/index.html), [스타일](../renderer/styles.css), [화면 로직](../renderer/app.js)은 Electron과 분리돼 있습니다. 폭 760px 이하에서 접는 검색·카테고리, 하단 탭, 월간 달력의 색 점과 선택 날짜 목록을 이미 제공합니다. **주간·일간 시간표는 현재 PC 중심 구성**이어서 휴대폰용 조작과 표시를 더 다듬어야 합니다.
- [반복 일정](../renderer/recurrence.js), [공휴일](../renderer/holidays.js), [빠른 입력](../renderer/quickadd.js)의 규칙과 테스트는 웹 화면을 유지하는 방식에서 재사용하기 좋습니다.
- [저장 어댑터](../renderer/storage.js)는 Electron의 `window.storage`가 있으면 IPC를 사용하고, 없으면 브라우저 `localStorage`를 사용합니다. 따라서 일반 브라우저에서도 화면은 실행되지만 **PC의 JSON 파일과 휴대폰 데이터가 자동으로 연결되지는 않습니다.**
- [preload](../preload.js)가 제공하는 저장 폴더·백업·외부 변경·종료 전 저장 API는 [main](../main.js)과 [store](../store.js)에 의존합니다. 모바일 브라우저와 모바일 앱에는 Electron의 preload가 없으므로 이 연결을 다른 저장·기기 API로 대체해야 합니다.
- 현재 일정 알림은 [main](../main.js)의 실행 중인 프로세스가 주기적으로 검사합니다. 이 코드를 웹에 복사한다고 휴대폰에서 앱을 닫은 뒤에도 계속 실행되는 것은 아닙니다.

저장 어댑터 파일에 ‘서버로 옮길 때 이 파일만 바꾸면 된다’는 설명이 있지만, 실제 PC·휴대폰 동기화에는 아래의 로그인·충돌 처리·오프라인 재전송·기기별 알림까지 함께 설계해야 합니다.

## 선택지 비교

작업 범위는 **현재 화면을 기준으로 비교한 상대적 크기**입니다. 날짜나 비용 견적이 아니며, 계정 동기화와 알림을 어디까지 포함하느냐에 따라 달라집니다.

| 선택지                        | 재사용할 수 있는 부분                                                                  | 새로 해야 하는 핵심 작업                                                                        | 상대적 작업 범위                                                                                                            |
| ----------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 웹/PWA                        | 기존 HTML·CSS·JavaScript 화면과 일정 규칙을 대부분 유지                                | 휴대폰 주간·일간 화면, IndexedDB 저장, HTTPS·설치 정보·오프라인 처리, 필요하면 계정 동기화      | 화면 재사용이 가장 많음. 개인 기기 로컬 사용부터 시작하면 가장 작지만, 신뢰할 수 있는 동기화·백그라운드 알림은 별도 큰 작업 |
| Capacitor 기반 iOS·Android 앱 | 기존 웹 화면을 모바일 WebView에 담고 일정 규칙을 재사용                                | Electron 대신 모바일 플러그인 어댑터, 기기 저장·알림·공유·파일 선택, 두 플랫폼의 빌드·서명·검수 | 화면 재사용은 높음. PWA의 공통 데이터 작업에 네이티브 연결과 두 OS 운영 작업이 추가됨                                       |
| React Native 앱               | 데이터 형식·규칙·예시·테스트 아이디어. 순수 JS 규칙은 호환성을 확인해 일부 재사용 가능 | DOM·CSS 기반 화면을 네이티브 컴포넌트로 다시 구현, 데이터·알림 어댑터, 두 플랫폼 배포           | 화면 재작성 때문에 큼. 현재 HTML·CSS를 그대로 쓰는 방식이 아님                                                              |
| Flutter 앱                    | 기능 정의·데이터 형식·테스트 사례·디자인 방향                                          | Dart로 화면과 규칙을 이식하거나 재구현, 데이터·알림 어댑터, 두 플랫폼 배포                      | 기존 JS 화면과 규칙의 직접 재사용이 적어 초기 전환 범위가 가장 큰 편                                                        |

React Native·Flutter를 선택하면 OS에 맞는 화면과 상호작용을 설계할 여지가 커집니다. 그만큼 현재 화면을 다시 만드는 비용을 감수해야 하며, 어떤 도구도 계정 동기화·백업·알림·스토어 배포를 자동으로 완성해 주지는 않습니다.

## 어느 방식이든 필요한 모바일 정리

1. **휴대폰에서 쓰기 좋은 화면:** 주간·일간 시간표, 일정 길게 누르기/이동, 작은 버튼, 날짜·시간 입력, 키보드가 열린 폼, 뒤로 가기, 가로 보기, 노치·하단 안전 영역을 실제 기기로 확인합니다. 기존 데스크톱 드래그 조작을 그대로 두는 것만으로 완료하지 않습니다.
2. **저장 성공 기준:** 화면에서 추가한 내용이 실제 저장된 뒤 성공으로 표시되도록 유지합니다. 휴대폰은 앱을 갑자기 중단할 수 있으므로 PC의 종료 확인창이나 종료 직전 저장에 의존하지 않고 변경 시점에 저장합니다. 백그라운드 전환·재시작·저장 공간 부족도 검사합니다.
3. **데이터 이동과 복구:** 기존 PC 데이터의 가져오기·내보내기, 데이터 형식 버전, 손상·부분 실패, 백업 복원을 검증합니다. 브라우저 저장소나 앱 로컬 DB만 있는 상태를 원격 백업으로 표현하지 않습니다.
4. **PC·휴대폰 공용 데이터가 필요하다면:** 아래의 비공개 계정 동기화 작업을 별도 범위로 잡습니다. ‘모바일에서 화면이 보임’과 ‘PC의 같은 일정이 보임’은 서로 다른 완료 조건입니다.

## 웹/PWA로 만드는 경우

PWA는 웹앱을 홈 화면에 추가하고 오프라인 사용을 보완하는 방향입니다. 브라우저별 설치 UI와 지원 조건은 다르므로 대상 기기에서 확인합니다.

- **배포와 설치:** HTTPS 주소, 앱 이름·아이콘·시작 주소·표시 모드를 담은 Web App Manifest, 적절한 서비스 워커 범위를 준비합니다. 포트폴리오 전체를 제어하지 않도록 앱 전용 경로와 캐시 범위를 분리하는 편이 좋습니다.
- **오프라인 화면과 업데이트:** 서비스 워커로 필요한 정적 파일을 캐시하고, 첫 실행의 온라인 필요 여부·캐시 갱신·구버전 화면과 새 데이터 형식의 호환성을 정합니다. 서비스 워커를 추가하는 것만으로 일정 데이터까지 자동 저장되지는 않습니다.
- **데이터 저장:** 현재 `localStorage` 대체 경로를 그대로 최종 저장 설계로 삼기보다 IndexedDB 기반 저장·버전 변경·재시도·오류 표시를 구현합니다. 저장소 지속성 요청과 용량 부족·정리 가능성을 고려합니다. IndexedDB도 사용자가 사이트 데이터를 지우거나 OS가 저장소를 정리하면 데이터가 사라질 수 있으므로 내보내기 또는 동기화 백업이 필요합니다.
- **종료와 백그라운드:** 서비스 워커는 항상 켜져 있는 PC 프로세스가 아닙니다. `setInterval`로 몇 초마다 확인하는 PC 알림 방식을 그대로 가져갈 수 없습니다. 앱이 닫혔을 때의 알림이 필요하면 Web Push 권한·구독·서버 발송 등을 따로 설계하고, 오프라인·권한 거부·OS 제한 때의 동작을 정해야 합니다.
- **iPhone/iPad:** Web Push는 지원 OS와 홈 화면에 설치된 웹앱 등 조건이 있습니다. 일반 Safari 탭에서 보는 것과 홈 화면 웹앱을 같은 조건으로 간주하지 않습니다. 실제 대상 iOS 버전·설치 방식·알림 허용 상태에서 검사해야 합니다.

PWA에서 모든 기기의 정확한 시각 알림이나 PC처럼 상시 실행을 약속하지 않습니다. 일정 알림이 핵심이라면 실제 지원 범위를 먼저 검증해 이 선택지가 충분한지 판단합니다.

## Capacitor로 기존 화면을 감싸는 경우

Capacitor는 현재 웹 화면을 살리면서 Android·iOS의 네이티브 API를 연결하는 선택지입니다. **Electron 프로젝트 자체를 변환하는 도구는 아니므로** `main.js`, `preload.js`, Node의 `fs` 저장소는 그대로 실행되지 않습니다.

- `PlannerStorage`와 필요한 `PlannerNative` 동작을 모바일 로컬 DB·파일·공유·알림 플러그인에 맞게 구현합니다. Windows 트레이·시작 프로그램 등록을 휴대폰에 동일하게 옮기기보다 모바일에 필요한 설정으로 구분합니다.
- 휴대폰의 앱 전용 저장 영역과 파일 선택 권한을 사용합니다. PC처럼 임의의 OneDrive 폴더에 JSON을 계속 쓰는 방식이 그대로 가능하다고 가정하지 않습니다. PC·휴대폰 동기화가 목적이면 계정 기반 방식과 비교해 결정합니다.
- 로컬 알림을 OS에 예약하거나 푸시 알림을 연동할 수 있지만, 권한·배터리 정책·예약 제한·재부팅 등의 조건을 기기별로 검사해야 합니다. 네이티브 앱도 무제한 백그라운드 실행을 보장하지 않습니다.
- Android 프로젝트와 iOS 프로젝트 각각의 빌드·권한 설명·테스트·버전 관리를 준비합니다. 기존 웹 화면을 재사용해도 이 운영 작업은 남습니다.

## React Native·Flutter로 새 화면을 만드는 경우

캘린더의 모바일 사용 방식부터 다시 설계할 때 고려할 수 있습니다. Capacitor와 마찬가지로 스토어 앱을 만들 수 있는 선택지이며, 화면 재작성으로 얻을 사용성 개선이 현재 화면 재사용보다 중요한지 비교합니다.

- React Native는 HTML DOM·현재 CSS를 네이티브 화면으로 다시 작성합니다. `recurrence.js` 같은 순수 JS 로직은 Node·브라우저 전역 의존성을 점검한 뒤 재사용할 수 있지만, 기존 화면 테스트를 그대로 네이티브 UI 테스트로 사용할 수는 없습니다.
- Flutter는 Dart 기반이므로 현재 JS 로직도 이식·재검증해야 합니다. 반복 일정·공휴일·입력 해석의 원본 테스트 사례는 변환 후 결과를 비교하는 기준으로 활용할 수 있습니다.
- 두 방식 모두 캘린더 표시·입력·접근성, 로컬 저장소, 오프라인 동기화, 알림, 데이터 가져오기와 배포 검사를 별도로 완성해야 합니다.

## PC·휴대폰 계정 동기화는 별도 공통 작업

현재 Windows 앱의 저장 파일이나 홈페이지의 프로젝트 관리용 Supabase 설정만으로 개인 일정 동기화가 생기지 않습니다. 동기화를 선택하면 다음 작업이 공통으로 필요합니다.

- 사용자 로그인·세션 관리와 **본인 일정만 읽고 쓰는 권한**을 설계합니다. 홈페이지의 공개 프로젝트 목록과 개인 일정 테이블·접근 정책을 구분하고, 비밀 키를 클라이언트에 넣지 않습니다.
- PC·휴대폰 모두 같은 데이터 규칙을 사용하는 동기화 어댑터를 만듭니다. 전체 JSON을 마지막 저장으로 덮어쓰는 현재 방식만으로 두 기기의 동시 변경을 안전하게 합칠 수는 없습니다.
- 항목 ID·변경 버전·삭제 기록·충돌 처리, 오프라인 변경 대기열·재연결 재전송·중복 방지, 시간·날짜·반복 일정의 일관성을 검증합니다.
- 서버 백업·데이터 내보내기·계정 삭제·다른 계정으로 바꿨을 때의 로컬 데이터 처리를 정합니다. 개인 일정과 백업 파일을 공개 사이트의 HTML·예시 데이터·정적 캐시에 포함하지 않습니다.

## 모바일 앱의 빌드·배포에서 남는 일

Capacitor·React Native·Flutter 어느 쪽이든 Android·iOS 설치 패키지를 각각 만들어야 합니다. 스토어로 공개한다면 개발자 계정, 앱 식별자, 서명 키·인증서, 권한·개인정보 설명, 스크린샷과 심사 준비가 필요합니다.

- **Android:** Android SDK·빌드 도구, 서명 키 보관, 기기 검사, 테스트 배포를 준비합니다. Google Play 공개는 Play Console과 해당 시점의 배포·검수 조건을 확인합니다.
- **iOS:** macOS/Xcode 기반 빌드 환경, 서명·프로비저닝, 실제 iPhone 검사와 테스트 배포를 준비합니다. App Store/TestFlight 배포는 Apple Developer·App Store Connect 조건을 확인합니다.
- 공개용 스토어 계정·서명은 현재 Windows 설치 파일의 GitHub Releases 배포나 SmartScreen 안내로 대신되지 않습니다. 스토어 외 테스트 배포도 각 OS가 허용하는 설치·서명 절차를 따라야 합니다.

## 권장 검토 순서

1. 먼저 현재 PC 설치 버전을 실제로 사용하고, 남은 9개 항목의 수동 결과를 기록합니다.
2. **PC 설치 앱 + 휴대폰 스토어 앱이라는 목표를 유지하면서** 필요한 범위를 정합니다. PC와 같은 일정이 보여야 하는지, 오프라인 입력과 앱을 닫은 뒤 알림이 필요한지를 정하고 공통 데이터 설계를 준비합니다.
3. 기존 코드를 최대한 살려 App Store·Google Play 앱을 만드는 것이 우선이면 **Capacitor를 먼저 검토**합니다. 실제 휴대폰에서 현재 화면, 로컬 저장·알림 플러그인, 권한과 두 플랫폼의 빌드·서명을 검증합니다. 단순히 웹 화면을 감쌌다는 이유로 완성된 모바일 앱으로 판단하지 않습니다.
4. 현재 웹 화면을 유지해서는 원하는 모바일 조작을 만들기 어렵거나 전체 화면 재설계가 필요하면 React Native·Flutter의 재작성 범위를 비교합니다. PWA는 원한다면 더 작은 범위의 사용성·플랫폼 기능 실험으로 활용할 수 있지만, **스토어 앱 목표의 대체안으로 자동 전환하지 않습니다.** 홈페이지 예시 미리보기도 개인 일정 앱으로 간주하지 않습니다.
5. 선택한 스토어 앱 경로에서 저장 실패·재시작·오프라인·알림 권한·데이터 이동을 검증하고, 계정 동기화·테스트 배포·스토어 공개 범위를 확정합니다. 이 문서만으로 새 기능 개발을 시작하지 않습니다.
