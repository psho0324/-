# 계정 로그인과 개인 데이터 동기화 설계

작성일: 2026-11-10 · 상태: 설계 초안, 구현되지 않음

현재 PC 앱은 로그인 없이 로컬 JSON 파일을 저장합니다. 계정 동기화를 추가한다면 **기존 로컬 사용을 유지하고, 사용자가 선택한 자료만 본인 계정의 비공개 데이터로 옮기는 방식**을 권장합니다. 홈페이지의 공개 프로젝트·제작 기록과 개인 일정·할 일을 별도 자료로 취급합니다.

이 문서는 저장 구조와 동기화 규칙을 검토하기 위한 문서입니다. 앱 코드, SQL, 정책, 로그인 화면, 서버, 배포 설정을 변경하지 않았습니다. Windows 설치 앱의 기존 수동 확인 항목은 사용자가 따로 확인하며, 여기서는 그 결과를 추정하지 않습니다.

## 1. 현재 코드에서 확인한 사실

## 2. 무엇을 동기화할지 먼저 분리하기

| 자료                                                                | 권장 범위           | 이유                                                                                                                                                                  |
| ------------------------------------------------------------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `events`와 `todos`                                                  | 본인 계정           | 일정·할 일 본문, 기한, 완료 상태를 다른 기기에서도 이어서 사용합니다.                                                                                                 |
| 앱의 `projects`와 `categories`                                      | 본인 계정           | 목표·카테고리와 연결된 항목을 함께 보존합니다.                                                                                                                        |
| `events.doneOn`, `todos.completedAt`, `projects.completedAt`        | 관련 항목과 함께    | 완료 통계의 근거입니다. 예전 항목에 없는 완료 시각을 이주 시각으로 채우지 않습니다.                                                                                   |
| `settings.taskTrackingSince`                                        | 계정의 데이터 기준  | 추적 시작일을 잃으면 오래된 일정이 한꺼번에 밀린 일로 바뀔 수 있습니다. 처음부터 새로 설정하지 않습니다. 여러 자료를 합칠 때의 기준일 선택은 미리보기에서 확인합니다. |
| `settings.weekStart`, `settings.holidays`                           | 계정 설정 후보      | 기기 공통 사용을 제안하되 최초 구현 전에 범위를 확정합니다.                                                                                                           |
| `settings.autoStart`, `settings.keepRunning`                        | 기기 전용           | Windows 시작 등록과 트레이 상주 여부를 다른 PC에서 켜거나 끄지 않습니다.                                                                                              |
| `settings.notifications`                                            | 우선 기기 전용      | PC마다 알림을 다르게 받을 수 있습니다. 일정의 `reminder` 값과 OS 알림 허용 상태도 구분합니다.                                                                         |
| `settings.defaultView`, `settings.hiddenCategories`                 | 우선 기기 전용      | 화면 보기·필터가 다른 PC의 사용 상황을 덮지 않도록 합니다. ID 변환 시 로컬 필터 참조도 바꿉니다.                                                                      |
| `planner-config.json`의 `dataDir`                                   | 기기 전용           | 실제 저장 폴더 경로입니다. 다른 PC에는 같은 경로가 없을 수 있고 계정으로 보낼 필요가 없습니다.                                                                        |
| `storage.info()`의 `dataFile`, `defaultDir`, `backupDir`, `problem` | 기기 전용           | 운영 경로·오류 정보이며 일정 내용이 아닙니다. 서버 자료에 넣지 않습니다.                                                                                              |
| `backups/` 및 손상 파일 사본                                        | 기기 전용           | 현재 로컬 복구 수단을 유지합니다. 기존 백업 전체를 자동 업로드하지 않습니다.                                                                                          |
| 인증 세션·기기 ID·동기화 대기열·커서                                | 각각 별도 로컬 상태 | 일정 백업·공유 폴더·홈페이지 공개 파일과 섞지 않습니다.                                                                                                               |

현재는 일부 기기 전용 설정도 `planner-data.json`에 함께 들어 있어 공유 폴더로 전달될 수 있습니다. 향후 계정 동기화에서는 업로드 직전에 제외하는 것에 그치지 않고, 로컬 저장·가져오기·복원 단계에서도 사용자 내용과 기기 설정을 분리해야 합니다. 첫 이전 때 각 PC의 기존 기기 설정을 별도 보존하고, 서버에서 내려받은 내용으로 OS 자동 시작 설정을 변경하지 않습니다.

## 3. 계정·항목 식별과 기존 ID 이전

### 소유자와 항목의 식별

- 소유자 키는 로그인으로 확인된 Supabase 사용자 `user.id`를 사용합니다. 이메일·닉네임은 변경될 수 있으므로 소유자 키가 아닙니다.
- 일정·할 일·목표·카테고리는 각각 고유한 UUID를 갖도록 합니다. 서버 자료에는 소유자 ID, 항목 종류, 항목 UUID를 함께 기록합니다.
- 관계는 같은 소유자 안에서만 연결합니다. 할 일의 목표, 항목의 카테고리가 다른 소유자의 UUID를 가리키는 요청은 거절합니다. 단순히 화면에서 숨기는 것으로 끝내지 않습니다.
- 홈페이지의 `calendar` 프로젝트 ID는 앱 소개 카드의 ID로만 남습니다. 개인 일정·개인 계정과 연결하는 공용 컨테이너로 사용하지 않습니다.

### 기존 문자열 ID를 안전하게 옮기는 절차

1. 사용자가 이전을 선택하면 현재 로컬 자료를 먼저 백업하고 읽기 전용으로 분석합니다. 분석 단계에서 원본 파일을 덮어쓰거나 서버에 보내지 않습니다.
2. 이 자료 묶음에 `legacy_dataset_id`라는 임의의 식별자를 한 번 부여하고, 이전 작업·대상 계정·자료 버전과 함께 로컬 이전 기록에 보관합니다. 이 이름은 제안이며 아직 코드에 없습니다.
3. 종류별로 기존 ID → 새 UUID 대응표를 만듭니다. 정상 UUID도 충돌 여부를 확인합니다. 같은 문자열이 서로 다른 종류에 있다고 같은 항목으로 취급하지 않습니다.
4. `categoryId`, 할 일의 `projectId`, 로컬 `hiddenCategories`, 반복 회차의 일정 ID 참조를 대응표로 함께 바꿉니다. `exceptions`와 `doneOn`의 날짜 키, 실제 완료 시각, 반복 규칙·기한·메모·색은 그대로 보존합니다.
5. 중복 ID·잘못된 참조·해석하지 못한 항목을 미리보기에 표시합니다. 관계가 모호한 자료를 임의로 버리거나 이름으로 합치지 않습니다. 수정 또는 제외할 항목을 확인한 뒤 원본과 분리한 이주 사본을 만듭니다.
6. 대응표와 작업 ID를 보존해 재시도 시 같은 UUID를 사용합니다. 서버는 대상 계정과 이전 작업 ID별 수신 기록을 두어 응답 유실 후 재시도가 중복 항목을 만들지 않게 합니다.
7. 서버 적용이 확인된 뒤에만 이 PC의 해당 계정 프로필을 새 형식으로 전환합니다. 이전 원본과 백업은 롤백용으로 남깁니다.

이름·제목·날짜가 같다고 같은 자료는 아닙니다. 특히 서로 다른 PC의 `c-work`가 사용자에 의해 다르게 수정됐을 수 있습니다. 새 계정의 기본 카테고리는 한 번만 만들고, 기존 자료와 합칠 때에는 대응표를 미리 보여줍니다. 서버에 이미 자료가 있다면 자동 덮어쓰기 대신 별도 항목으로 추가하거나 사용자가 연결을 선택하도록 합니다.

같은 이전 작업의 재시도와, 별개 파일을 다시 가져오는 행위도 구분합니다. 파일 해시는 같은 사본인지 판단하는 참고값이지 소유권 증명이나 유일한 자료 식별자가 아닙니다. 이전 기록이 없는 다른 PC의 파일에는 중복 가능성을 표시하고 사용자가 이전 대상을 확인하게 합니다.

## 4. 서버와 로컬에 필요한 상태

아래는 논리적인 자료 목록입니다. 실제 테이블 이름이나 SQL은 정하지 않았습니다.

| 구분             | 필요한 상태                                                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 본인 항목        | 소유자, UUID, 종류, 내용, 참조 관계, 서버 생성 시각, 서버 수정 시각, 항목 버전, 삭제 표시                                            |
| 변경 기록        | 소유자별 변경 순번, 항목 UUID·종류·버전, 그때의 내용 또는 삭제 표시                                                                  |
| 요청 처리 기록   | 소유자와 요청 UUID, 요청 내용 식별값, 적용 결과. 같은 요청의 재전송은 같은 결과를 반환하고 다른 내용으로 같은 UUID를 재사용하면 거절 |
| 기기별 수신 상태 | 임의의 기기 ID, 계정, 마지막 확정 커서, 동기화 세대, 마지막 확인 시각                                                                |
| 로컬 항목        | 서버에서 받은 기준 버전·기준 사본, 아직 전송하지 않은 변경, 충돌 사본                                                                |
| 로컬 전송 대기열 | 요청 UUID, 대상 계정·항목, 변경 종류, 기준 버전, 전송 내용, 재시도 상태                                                              |
| 이전 기록        | 자료 묶음 ID, 대상 계정, 이전 작업 ID, ID 대응표, 완료된 부분과 복구 정보                                                            |

기기 ID는 임의의 UUID를 제안합니다. Windows 사용자명·컴퓨터명·실제 폴더 경로를 동기화 식별자로 삼지 않습니다. 영속 기기 ID와 서버가 인정한 로그인 세션은 서로 다른 개념입니다.

### 수정 시각과 버전의 역할

서버가 승인한 변경에 서버 수정 시각과 증가하는 버전을 부여합니다. 클라이언트가 보낸 현재 시각을 그대로 신뢰하거나, 가장 큰 `Date.now()`가 무조건 이기게 하지 않습니다. PC 시계가 빠르거나 오프라인에서 오래 편집한 경우에도 시간 비교만으로 다른 기기의 변경을 지우지 않도록 합니다.

항목 버전은 동시 수정 판정에 사용하고, 변경 순번은 내려받기 커서에 사용합니다. 두 값의 역할을 섞지 않습니다. 기기의 수정 시각은 사용자 설명이나 진단용 보조 자료로만 둘 수 있습니다. 현재의 `createdAt`·`completedAt`·`doneOn`은 업무 내용·정렬·통계 자료이지 동기화 승패 기준이 아닙니다.

## 5. 오프라인 저장·재시도·충돌 규칙

### 기본 흐름

1. 편집은 우선 로컬에 저장하고, 같은 로컬 저장 단위에서 계정이 정해진 전송 대기열에 기록합니다. 앱 종료 직전 변경도 다음 실행 때 전송할 수 있어야 합니다.
2. 인증된 연결이 생기면 서버 변경을 내려받아 기준 상태를 갱신하고, 대기 변경의 기준 버전과 비교합니다. 서버 자료를 내려받았다는 이유로 아직 전송하지 않은 로컬 편집을 덮지 않습니다.
3. 전송에는 항목의 기준 버전과 요청 UUID를 넣습니다. 서버는 소유자·관계·내용·버전을 확인한 뒤 적용하거나 충돌로 응답합니다.
4. 응답을 잃으면 동일 요청을 재전송합니다. 서버 승인과 로컬 승인 기록 사이에서 앱이 꺼져도 중복 생성되지 않게 합니다.
5. 만료된 로그인, 권한 오류, 충돌, 연결 장애를 구분합니다. 로그인 오류를 무한 재시도하거나 실패한 항목 하나 때문에 다른 자료를 삭제하지 않습니다.

로컬 디스크 저장 성공과 서버 반영 성공은 별개입니다. 향후 화면도 그 둘을 구분해 알려야 합니다. 현재의 저장 실패 안내를 계정 동기화 성공 안내로 바꿔 부르지 않습니다.

### 충돌과 삭제

| 상황                                    | 초기 구현에서 권장하는 규칙                                                                                                                               |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 다른 항목을 각 PC에서 편집              | 각 항목 버전을 검사해 각각 적용합니다. 전체 JSON 하나의 버전 충돌로 만들지 않습니다.                                                                      |
| 같은 항목을 같은 기준 버전에서 편집     | 먼저 승인된 수정만 해당 버전에 적용합니다. 나중 요청은 충돌 사본으로 보존하고 두 내용을 보여 선택하게 합니다. 초기에는 자동 필드 병합을 하지 않습니다.    |
| 서버에서는 삭제, 오프라인 PC에서는 수정 | 삭제된 항목으로 복원하는 일반 수정 요청은 거절합니다. 오프라인 수정은 로컬 충돌 사본으로 남기고, 사용자 선택에 의한 복원이나 새 항목 만들기만 허용합니다. |
| 오프라인 삭제와 다른 PC 수정            | 삭제도 기준 버전을 검사합니다. 최신 수정이 있으면 충돌을 알리고 그 내용을 확인한 후 삭제 여부를 선택합니다.                                               |
| 삭제 취소·백업 복원                     | 현재 삭제 버전을 기준으로 한 명시적 복원 동작으로 처리합니다. 오래된 백업이나 대기열을 업로드하는 것만으로 삭제가 취소되지 않습니다.                      |
| 목표·카테고리 삭제                      | 현재 앱의 연결 해제·일정 색 보존 의미를 유지합니다. 삭제 표시와 관계 변경을 같은 서버 작업으로 적용하고, 중간에 끊긴 상태로 내려받지 않게 합니다.         |

현재의 파일 동기화 방식처럼 삭제된 항목을 응답에서 빼기만 하면, 오래 오프라인이었던 PC가 그 항목을 새 자료로 다시 올릴 수 있습니다. 따라서 서버는 삭제 표시인 **tombstone**을 버전과 함께 저장·전달해야 합니다.

삭제 기록을 보관하는 기간은 추후 결정합니다. 기간이 지났다는 이유만으로 삭제된 UUID를 새로운 항목으로 다시 받아서는 안 됩니다. 최소 삭제 식별 기록을 남기거나, 오래된 기기의 동기화 세대를 만료시키고 전체 재대조 후에만 전송을 허용하는 방식을 함께 설계합니다. 삭제 정보 압축 이전의 커서를 가진 기기는 곧바로 업로드하지 못하게 합니다. 계정 삭제 시에는 해당 계정의 이 기록까지 삭제하는 별도 절차가 필요합니다.

### 안전한 변경 커서

단순한 PC 시각이나 `(updated_at > 마지막 시각)`만으로 변경을 가져오지 않습니다. 같은 시각의 여러 변경, 늦게 확정되는 작업, 삭제 자료, 페이지 중간 실패를 처리해야 합니다.

권장안은 소유자별 쓰기를 짧은 서버 트랜잭션으로 직렬화하고, 그 안에서 변경 순번을 확정하는 방식입니다. 항목·삭제 표시·변경 기록·요청 수신 기록을 같은 작업으로 확정합니다. 일반 증가 번호를 미리 발급하고 완료 순서를 고려하지 않는 방식은 먼저 발급된 작업이 나중에 확정될 때 누락을 만들 수 있으므로 피합니다.

내려받기는 확정된 변경의 상한을 먼저 정하고, 변경 기록을 그 상한까지 순서대로 페이지 조회합니다. 각 페이지의 변경·삭제·관계와 다음 커서를 로컬에 함께 저장한 뒤 커서를 전진시킵니다. 중간에 앱이 꺼지면 이전 확정 커서부터 다시 읽어도 같은 결과가 나와야 합니다. 항목의 현재 내용만 덮어쓰는 기록이 아니라 해당 순번의 내용·삭제 상태를 복원할 수 있는 변경 기록이 필요합니다.

실시간 알림을 추가하더라도 새 변경이 있다는 신호로만 사용합니다. 놓친 변경은 커서 기반 조회로 복구하고, 페이지 조회 결과만으로 클라이언트의 미전송 수정 사본을 삭제하지 않습니다.

## 6. 기존 Supabase를 함께 쓸지

| 선택                              | 장점                                                                                    | 비용·위험과 필요한 분리                                                                                                                                                                      |
| --------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 홈페이지와 같은 Supabase 프로젝트 | 프로젝트·인증·운영 관리가 적고 초기 연결 구성이 단순합니다.                             | 인증 사용자 풀과 자원·장애 영향이 공유됩니다. 개인 자료용 테이블·함수·정책·버킷을 따로 만들고, 공개 CMS의 읽기·관리자·이미지 정책을 그대로 복사하지 않아야 합니다.                           |
| 플래너 전용 Supabase 프로젝트     | 공개 홈페이지와 개인 자료의 운영 경계, Auth 설정, API 자원·장애 영향을 나누기 쉽습니다. | 프로젝트·인증·백업·운영 비용과 관리가 늘 수 있습니다. 홈페이지 관리자 계정과 플래너 계정이 자동으로 같아지는 것도 아니며, 서로 다른 프로젝트의 사용자 ID를 임의로 같다고 취급할 수 없습니다. |

개인 일정의 비공개 분리를 우선한다면 **플래너 전용 프로젝트**를 권장합니다. 같은 프로젝트를 쓰는 것도 가능하지만, 공개 CMS와 사용자 계정이 섞이는 범위를 검토한 뒤 선택해야 합니다. 이 문서에서 프로젝트를 만들거나 운영 설정을 변경하지는 않습니다.

같은 프로젝트를 선택할 때도 `public.projects`, `workspace_items`, `workspace_history`, `workspace_requests`, `workspace-media`를 플래너 자료 저장소로 재사용하지 않습니다. 홈페이지를 공개 읽기로 유지하는 요구와 개인 일정을 본인만 읽는 요구가 다르기 때문입니다. 공개 CMS의 `revision`·요청 중복 처리 발상은 참고할 수 있지만 접근 권한과 자료 모델은 별도로 설계합니다.

## 7. 본인만 접근하는 서버 권한

- 로그인하지 않은 요청에는 개인 일정·목표·카테고리·설정·삭제 기록·변경 기록·첨부 파일을 읽거나 쓸 권한을 주지 않습니다. 개인 자료에는 CMS식 `published` 공개 전환을 두지 않습니다.
- 인증된 사용자도 각 자료의 소유자가 현재 `auth.uid()`와 일치할 때만 접근하도록 합니다. 읽기·수정·삭제 대상 확인과 새 자료·수정 결과의 소유자 확인을 모두 적용합니다.
- 클라이언트가 보낸 `owner_id`만 믿지 않습니다. 서버에서 인증 세션의 사용자와 대조하며 다른 사람으로 소유자를 바꾸는 요청을 거절합니다.
- 목표·카테고리 참조와 변경 기록·요청 영수증·이전 기록에도 같은 소유자 경계를 적용합니다. 본문만 가리고 제목·삭제 이력·개수 같은 자료를 다른 사용자에게 노출하지 않습니다.
- 새 계정을 홈페이지의 `site_admins`에 넣지 않습니다. 반대로 홈페이지 관리자라는 이유만으로 다른 사람의 플래너 자료를 앱 API에서 열람할 수 있게 하지 않습니다.
- 가능하면 RLS가 그대로 적용되는 접근 방식을 사용합니다. 소유권 검사를 대신하는 권한 높은 서버 함수를 만들 경우, 그 함수의 호출 권한·소유자 검증·다른 소유자 참조 차단까지 별도 검토해야 합니다.
- 개인 첨부 파일이 필요해지는 경우 전용 비공개 버킷과 본인 소유 정책을 설계합니다. 현재의 `workspace_media_access`는 공개 자료의 참조를 통해 익명 읽기를 허용하므로 개인 파일 정책으로 사용하지 않습니다.
- 공개용 API 키는 사용자 권한 검증을 대신하지 않습니다. 서비스 관리자 비밀 키를 PC 앱·브라우저·저장소·설치 파일·공개 설정에 넣지 않습니다.

이 설계의 RLS는 일반 앱 사용자의 접근을 구분하기 위한 것입니다. 서버 운영자의 데이터베이스 관리 권한까지 없애거나 종단간 암호화를 제공한다는 뜻은 아닙니다. 그런 보호가 필요하면 별도 요구와 키 복구 설계가 필요합니다.

## 8. 최초 연결·로그아웃·계정 변경

### 로그인하지 않은 기존 사용

지금처럼 로컬 파일로 사용할 수 있어야 합니다. 로그인 화면을 열거나 계정을 만들었다는 이유만으로 기존 파일을 자동 업로드하지 않습니다. 홈페이지 iframe·샘플 미리보기는 개인 프로필·토큰·설치 앱 데이터를 읽지 않습니다.

### 사용자가 동기화를 처음 선택할 때

1. 연결할 계정을 확인하고 로컬 파일의 위치·현재 저장 완료 여부·이전 백업을 점검합니다. 기존 파일을 유지한 채 이전 전 백업을 만듭니다.
2. 업로드 후보의 종류·개수·연결 관계·제외되는 기기 설정·손상 또는 중복 가능성을 로컬 미리보기로 보여줍니다. 이 시점에는 본문을 서버로 전송하지 않습니다.
3. 해당 계정에 이미 자료가 있으면 별도로 내려받아 비교합니다. 다운로드만으로 로컬 원본을 바꾸지 않습니다. 추가·연결·이전하지 않기 중 어떤 처리를 할지 확인합니다.
4. 사용자가 승인한 묶음에만 이전 작업 ID를 부여해 전송합니다. 서버가 인증한 계정의 소유 자료로만 만들고, 다른 계정으로 처리 대상을 바꾸지 않습니다.
5. 중간 실패·응답 유실을 기록하고 같은 작업을 재개합니다. 일부만 적용된 상태를 완료로 표시하지 않습니다. 작업 묶음은 크기를 제한하고, 여러 묶음이라면 완료 범위를 서버·로컬 양쪽에 기록합니다.
6. 확인된 결과로 새 계정용 로컬 프로필을 활성화합니다. 원본 로컬 전용 프로필과 이전 전 백업은 남겨 두고, 되돌릴 때 선택할 수 있게 합니다.

롤백은 범위가 다릅니다. 로컬을 이전 전 상태로 되돌리는 것은 이미 서버로 전송된 자료를 지우지 않습니다. 서버의 이전 결과도 되돌리려면 그 작업이 만든 항목만 식별하고, 이후 다른 기기에서 수정된 자료를 지우지 않도록 현재 버전을 확인해야 합니다. 그 전까지는 로컬 동기화를 중지하고 원본으로 돌아갈 수 있게 합니다.

### 계정마다 자료를 구분하기

로컬 전용 프로필과 각 `user.id`별 프로필·대기열·커서·백업을 구분합니다. 이메일이 바뀌었다고 새 계정으로 취급하지 않으며, 같은 이메일이더라도 사용자 ID가 달라졌으면 옛 자료를 자동 인수하지 않습니다. 다른 계정으로 로컬 자료를 옮기는 경우는 새 이전 확인 절차가 필요합니다.

로그아웃 시에는 먼저 로컬 저장 상태와 미전송 변경을 알리고, 이전 계정의 동기화 작업을 중단합니다. 로그인 세대를 구분해 늦게 도착한 이전 계정 응답이 새 계정 화면이나 파일에 적용되지 않게 합니다. 이후 명시적으로 로컬 전용 화면이나 새 계정 프로필을 엽니다. 다른 계정 로그인 후 이전 계정의 전송 대기열을 보내지 않습니다.

로그아웃과 자료 삭제를 같은 동작으로 취급하지 않습니다. 공유 PC에서는 계정 자료를 이 기기에서 제거하거나 보호된 상태로 남길지 선택할 수 있어야 합니다. 원격 자료까지 삭제하는 기능은 별도 확인·설계 대상입니다. 로그아웃 중 미전송 자료를 조용히 지우거나, 다음 로그인 계정의 소유 자료로 바꾸지 않습니다.

### 인증 정보와 파일 동기화의 경계

설치 앱의 로그인 세션은 향후 main 프로세스가 관리하고 필요한 결과만 제한된 IPC로 화면에 전달하는 구성을 검토합니다. 세션을 지속 저장한다면 사용 가능한 OS 보안 저장소·암호화 수단을 확인하고, 사용할 수 없을 때 평문 공유 폴더에 저장하는 대체 방식을 쓰지 않습니다. 로그인 콜백·URL·세션 갱신·만료 처리도 구현 전에 정해야 합니다.

현재 홈페이지의 [backend.js](../../backend.js)는 관리자 세션을 `sessionStorage`에 보관하는 웹 페이지용 구현입니다. 그 저장 방식을 설치 앱의 영속 인증 저장소로 그대로 복사하지 않습니다. 인증 정보는 일정 JSON·백업·동기화 폴더·오류 로그·공개 HTML에 넣지 않습니다.

계정 동기화 프로필을 켠 자료를 기존 OneDrive/Google Drive 전체 JSON 동기화와 동시에 주 저장소로 운용하면 두 동기화 방식이 서로 덮을 수 있습니다. 초기 권장안은 **한 프로필에 하나의 동기화 방식**입니다. 기존 폴더 방식은 로컬 전용 프로필에서 유지하고, 계정 프로필은 계정별 로컬 캐시와 서버 변경 기록을 사용합니다. 단순 백업 내보내기와 실시간 양방향 동기화는 별개로 취급합니다.

## 9. 추후 구현 순서와 통과 조건

아래는 앞으로의 개발 단계 제안이며 이번 작업에서 실행하거나 통과시킨 테스트가 아닙니다.

1. **자료 계약과 분리**: 사용자 내용·기기 설정·계정 프로필·로컬 이전 기록의 형식을 확정합니다. 기존 JSON 사본으로 관계·반복·완료 통계가 보존되는지를 검토하고 원본을 유지합니다.
2. **서버 격리와 인증**: 같은/별도 Supabase 프로젝트를 결정하고 비공개 자료 경계를 만듭니다. 비로그인·다른 사용자·사이트 관리자·정상 소유자 각각의 읽기·쓰기·참조·파일 권한을 검증해야 합니다.
3. **동의한 자료만 최초 이전**: 이전 미리보기·백업·ID 대응·중복 요청·부분 실패·재개·로컬 롤백을 먼저 완성합니다. 로그인만으로 업로드되지 않는 것이 통과 조건입니다.
4. **한 기기의 서버 왕복**: 로컬 저장과 전송 대기열의 원자성, 서버 버전 검사, 로그인 만료, 네트워크 중단·응답 유실·앱 재시작을 검증합니다.
5. **두 기기와 오프라인**: 동시에 같은 항목 편집, 삭제와 수정 충돌, 오래된 기기의 재접속, 삭제 기록 압축, 커서 중간 실패, PC 시계 차이를 검증합니다. 자료가 조용히 사라지거나 삭제된 항목이 자동 부활하지 않아야 합니다.
6. **계정 전환과 배포 검토**: 미전송 변경이 있는 로그아웃, A 계정 응답 지연 후 B 계정 로그인, 공유 PC 캐시 처리, 예전 버전 클라이언트의 호환성을 확인합니다. 운영 권한·보관·복구 방침을 정한 뒤 공개 사용 범위를 넓힙니다.

## 10. 구현 전에 남은 결정

- 같은 Supabase 프로젝트를 쓸지, 개인 일정 전용 프로젝트를 만들지.
- 이메일·비밀번호, 이메일 링크, 외부 로그인 중 첫 인증 방식과 계정 복구 방식. 로그인 링크를 설치 앱으로 받는 경로도 포함합니다.
- 초기 이전의 단위와 이미 서버에 있는 자료의 연결·중복 표시 방식.
- 계정 동기화에 포함할 환경 설정, `taskTrackingSince`가 서로 다른 자료를 합칠 때의 기준.
- 기존 시간 문자열을 어떤 시간대로 해석할지. 종일 날짜와 지역 시각을 보존하고 임의로 `Z`를 붙이거나 UTC 변환하지 않습니다. 시간대 이동·반복 일정 의미는 따로 확정합니다.
- 같은 항목 충돌을 사용자가 비교·선택하는 방식과 보관 기간. `doneOn`의 날짜별 변경을 나중에 별도 기록으로 나눌지 여부.
- 삭제 기록·변경 이력·요청 처리 기록·오래된 기기 등록의 보관 기간, 전체 재대조 조건.
- 로그아웃한 PC에 남길 자료, 계정 삭제·복구·자료 내보내기의 범위와 처리 기간.
- 기존 공유 폴더 사용자에게 계정 프로필로 전환하는 절차와 이전 앱 버전의 동시 사용 제한.
- 예상 사용자 수·자료량·비용 한도·장애 시 운영 책임. 현재 사용량이나 과금 설정은 이 문서에서 확인하지 않았습니다.

현재 단계의 권장안은 로컬 사용과 개인 자료를 먼저 분리하고, 별도 비공개 저장 구조·명시적 이전·항목 버전·삭제 기록을 갖춘 뒤 계정 동기화를 구현하는 것입니다. 이 문서는 기존 앱에 로그인이나 서버 동기화가 이미 제공된다는 의미가 아닙니다.
